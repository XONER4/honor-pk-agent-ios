# Уточнения к API.md (как реализовано)

Всё из API.md реализовано без переименований. Ниже — решения там, где контракт молчит или допускает разные трактовки.

## Ответы, не описанные в контракте
| Эндпоинт | Ответ |
|---|---|
| `PATCH /v1/devices/me`, `POST /v1/devices/me/stats`, `POST /v1/notifications/read` | `{"ok":true}` |
| `DELETE …/messages/:id`, `POST …/clear` | `{"ok":true}` (изменения приходят кадрами WS) |
| `POST …/reaction`, `POST …/pin` | обновлённый `Message` |
| `POST /v1/media` | `201` + `AttachmentRef` |
| `POST /v1/admin/devices/:id/block` | детальный `DeviceSummary` (как `GET /v1/admin/devices/:id`) |
| `POST /v1/admin/chats/:chatId/ai` | `Chat` (с точки зрения админа) |
| `POST /v1/admin/notifications` | `{"ok":true,"count":<сколько устройств получили>}` |

## Коды ошибок
`bad_request` 400 (валидация), `unauthorized` 401 (нет/неверный/просроченный токен), `forbidden` 403, `blocked` 403,
`not_found` 404, `conflict` 409, `payload_too_large` 413, `unsupported_media_type` 415, `range_not_satisfiable` 416,
`rate_limited` 429, `model_not_allowed` 400, `ai_unavailable` 503, `upstream_error` 502, `google_not_configured` 503, `internal` 500.

## Устройства и статистика
- Один `installId` = одно устройство = один пользователь (`userId`); аккаунтов между установками нет.
  Повторная регистрация с тем же `installId` — тот же `deviceId`/`userId`/`adminChatId`, новый токен, старые отозваны.
  Заблокированное устройство при регистрации получает `403 blocked`.
- `overview.users` = число пользователей, `overview.installs` = счётчик новых `installId` (сейчас совпадают).
  `online` = устройства в `foreground`, `inBackground` = в `background`, `messagesToday` = все сообщения с 00:00 UTC.
- `installs` в карточке устройства — эвристика «сколько раз ставили на этот телефон»: число устройств с теми же
  `platform + deviceModel + deviceName`.
- `birthday` — строка `YYYY-MM-DD`; `language` — код вида `ru`, `en`, `pt-BR`.
- `GET /v1/admin/devices`: `query` — подстрока (без учёта регистра) по имени, модели, названию устройства, id, версии;
  `status=online` — все не-offline (foreground + background). Сортировка: сначала онлайн, затем по `lastSeen`.

## Чаты и сообщения
- `Chat.title`: у устройства — `"Администратор"`; у админа — `displayName` → `deviceName` → `deviceModel`.
- Для устройства `peerPresence/peerLastSeen/peerTyping` описывают сторону админа (любой подключённый админ;
  `peerTyping` также true, пока генерирует ИИ). Для админа — устройство.
- Идемпотентность: `clientId` уникален в пределах чата; повтор возвращает то же сообщение (200) без повторной рассылки;
  тот же `clientId` от другой стороны → 409.
- Вложения при отправке: достаточно `{ "id": "…" }`; `name/mime/size/url` сервер берёт из БД, клиент может уточнить
  `kind` (например `voice`), `durationMs`, `width`, `height`. Прикреплять можно только свои загрузки
  (админ — любые админские) или файлы, уже использованные в этом чате. До 10 вложений, текст до 10 000 символов.
- Удаление «у всех» оставляет «надгробие»: `deleted:true`, `text:""`, `attachments:[]`, реакции снимаются,
  закреп снимается; рассылается `message.updated`. Удаление «у себя» просто скрывает сообщение для этой стороны (без кадра).
  `scope` по умолчанию `me`.
- Очистка «у себя» скрывает все текущие сообщения для этой стороны, `chat.cleared` получает только эта сторона.
  Очистка «у всех» (только админ) удаляет сообщения физически, неиспользуемые файлы удаляются с диска, `chat.cleared` — обеим сторонам.
- Реакции: по одной от каждой стороны на сообщение; новый emoji заменяет прежний, `null` — снять.
  В `reactions` порядок участников — по времени реакции.
- Закреп: один на чат; закрепить может любая сторона; закрепление другого сообщения снимает прежнее
  (для обоих приходит `message.updated`).
- `readByPeer`: для сообщений `user` — прочитал ли админ; для `admin`/`ai` — прочитал ли пользователь.
  `unread` считает только сообщения собеседника (для устройства — от `admin` и `ai`), не удалённые и не скрытые.
- **Расширения** (не ломают контракт): `PATCH …/messages/:id` `{ "text" }` — редактировать своё сообщение
  (ставит `editedAt`, кадр `message.updated`); `POST …/chats/:chatId/read` `{ "messageId" }` — REST-аналог WS-кадра `read`.
  Оба доступны и под `/v1/chats`, и под `/v1/admin/chats`.
- Пустое тело с `Content-Type: application/json` трактуется как `{}`.

## WebSocket
- Неверный токен → рукопожатие отклоняется HTTP 401. Заблокированное устройство подключается, получает
  `{"t":"blocked","message":…}` и закрывается с кодом **4003**; то же при блокировке во время соединения.
- До первого кадра `presence` устройство считается `background`. `lastSeen` = время последнего кадра/закрытия сокета;
  пока сокет открыт — «сейчас». Offline — через 40 с без сокета (переподключение в этот промежуток offline не вызывает).
- Сокет без единого кадра дольше 75 с закрывается сервером (клиент шлёт `ping` каждые 25 с).
- Админ сразу после подключения получает `presence`-кадры всех не-offline устройств. Кадры `presence` админам
  отправляются также при изменении `typingIn`.
- `typing`: индикатор гаснет сам через 8 с без повтора `typing:true`; отправка сообщения гасит индикатор отправителя.
  Кадры `typing`, `read`, `message*`, `chat.cleared` получают устройство-владелец и все сокеты админов
  (в том числе собственные — клиенту нужно игнорировать своё эхо/дедуплицировать по `clientId`).
- `read`: указатель только растёт; кадр рассылается только при продвижении.
- Неизвестные кадры игнорируются; максимальный размер кадра 64 КБ.

## Медиа
- Загрузка: multipart, поле `file` (≤ 100 МБ). Необязательные текстовые поля формы: `kind`, `name`, `durationMs`,
  `width`, `height` (порядок полей любой). `kind` по умолчанию выводится из MIME (`image/*`, `video/*`, `audio/*`, иначе `file`).
- `GET /v1/media/:id`: токен в `Authorization` **или** `?token=` (для плееров без заголовков). Устройство может скачать
  свои загрузки и файлы из сообщений своего чата; админ — любые. Поддерживается один диапазон `Range`
  (`206`, `Content-Range`); мульти-диапазоны отдаются целиком (200); недопустимый → `416` + `Content-Range: bytes */size`.

## Уведомления
- Рассылка «всем» создаёт копию для каждого незаблокированного устройства (свой флаг `read`). `kind:"admin"`, `chatId:null`.
- `GET /v1/notifications?after=ISO` — строго позже `after`, до 200 штук, старые первыми (удобно как курсор).

## AI-прокси
- Принимает и токен устройства, и токен админа (лимиты отдельные: 60 запросов / 10 мин на устройство/админа).
- Проверяются только `model` (allow-list) и наличие `messages`; остальное тело уходит в DeepSeek как есть.
  Статус и `Content-Type` апстрима передаются клиенту без изменений (включая ошибки DeepSeek).
  Если клиент оборвал соединение — запрос к DeepSeek прерывается.

## Групповой ИИ
- Упоминание — отдельное слово (без учёта регистра): `Honer…`, `ИИ`, `AI`, `нейросеть…`, `бот/бота/боту/…`.
  Срабатывает на сообщения и пользователя, и админа — ответ сразу.
- «Прямой вопрос» — сообщение пользователя с `?` или начинающееся с вопросительного слова (кто/что/как/сколько/…,
  who/what/how/…). Если за 20 с после него не пришло сообщение от админа (или ИИ) — отвечает ИИ.
- Сообщения ИИ никогда не запускают ИИ. Один ответ на чат одновременно; повод, пришедший во время генерации,
  обрабатывается после неё.
- ИИ видит последние 30 неудалённых сообщений (`[Пользователь]`/`[Администратор]`, свои — как `assistant`).
- При включении/выключении ИИ сервер публикует в чат сообщение от `ai` («Honer AI присоединился к чату…» /
  «Honer AI покинул чат.»), чтобы обе стороны сразу увидели изменение через обычный кадр `message`.
  Новый `aiEnabled` клиент получает из `GET /v1/chats` (стоит перезапросить при сообщении от `ai`).

## Push (FCM)
- Data-only сообщения, все значения — строки: `type` (`message`|`notification`), `chatId` (`""` для уведомлений), `title`, `body`.
  Для сообщений `title` = `"Администратор"` или `"Honer AI"`, `body` — текст (≤ 200 симв.) или «📷 Фото»/«🎤 Голосовое сообщение»/…
- Отправляется только устройствам, которые сейчас не в `foreground` (по WS-presence), и только на сообщения admin/ai
  и уведомления. Токен, отвергнутый FCM (UNREGISTERED), удаляется. Админ-приложение push не получает (эндпоинта
  регистрации push-токена для админа в контракте нет) — оно живёт на WebSocket.

## Админ
- Вход по `adminKey` возвращает `email` = первый адрес из `ADMIN_EMAILS` (или `"admin"`), `name` = `"Администратор"`.
- Google: проверяются подпись, `aud` ∈ `GOOGLE_CLIENT_IDS`, срок; `email` (без учёта регистра) ∈ `ADMIN_EMAILS`.
- Токен админа действует 180 дней, затем `401` → повторный вход. 10 неудачных входов с IP за 15 мин → `429`.
- Все админы — одна логическая сторона `admin` (общие указатели прочтения, реакции, presence).

## Эксплуатация
- Один инстанс (presence, typing и лимиты — в памяти процесса); `numReplicas: 1` в `railway.json`.
- `DB_MODE=memory` — только для разработки/тестов (pg-mem — devDependency, в Docker-образе его нет).
- Тесты используют глобальный `WebSocket`, поэтому для `npm test` нужен Node ≥ 22 (сервер работает на Node ≥ 20).
